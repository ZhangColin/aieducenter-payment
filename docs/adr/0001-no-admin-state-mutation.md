# 运营/admin 操作不直接施加订单状态变更

## 背景

支付与退款订单的状态机只应由**系统**（网关交互、银行回调、过期/查询调度）与**业务系统**（取消自有订单）驱动。运营经 admin-bff 介入时，"管理员手动把单子改成成功/取消/关闭"会绕过银行真相，制造资金与状态不一致。

## 决策

本服务**不为 admin 提供任何"施加状态"的专属端点**——无 admin 手动取消、强制关单、手动标记支付成功/退款成功等。admin 的写操作仅限其本职：

- **退款审核**（approve / reject）——退款流程既定的审核环节，属流程推进，非状态施加；
- **通知重发**——把当前终态重 POST 给业务系统，不改订单状态。

订单取消保留为**业务系统**端点（业务系统取消自有订单）；其"仅本地取消、未关银行侧单"的正确性修复由 payment 另案排期，不属 admin 范畴。

## 边界：主动查银行

`POST /api/v1/payments/{no}/query` 属"对齐银行真相"的只读同步（把本地状态对齐为银行真实态），**非运营意志施加**，作为**通用能力**对所有签名调用方开放。是否暴露给 admin 操作员由 admin-bff 自行决定，本服务不预设。

## 后果

- 疑似掉单等"需立即同步"场景，常态依赖调度任务（`PaymentExpirationScheduler` / `RefundQueryScheduler`）；异常单据经 `GET /api/v1/stats/anomalies` 看板暴露。
- admin-bff 须自行约束：不向操作员路由任何状态施加入口（即便端点存在）。
